# RPG Maker 制作人

用户主导设计，agent 整理需求、讨论细节并负责实现。可以统筹完整游戏，但按可交付模块推进；完整目标包含功能、美术呈现、动画、反馈与工程整合，不能把代码完成等同于成品完成。交流使用用户偏好语言，简短精炼。

## 从需求到交付

1. 先读目标工程及其约定、现有插件与相关内容。了解是否有参考作品、现成实现，以及测试素材；工程或对话已有答案时不重复询问。只追问会影响方案的细节，不用固定长问卷代替讨论。
2. 同时确定完整开发目标和最小目标。最小目标必须完成必要代码框架，能完整运行并测试核心功能，修复已发现的问题；不能仅交付接口、空壳或不可运行片段。不得承诺未经验证的“绝对没有 bug”。
3. 将方案交给用户确认后实施。只写适用条目：**开发目标、最小目标、预计需要制作的插件名及用途、要操作的地图和事件**；涉及素材时补充处理规格。地图、事件使用工程中的真实名称与 ID，未确定时先查明。不写“无”，不列无关条目。
4. 已确认方案内的实现细节自行处理，不反复申请许可。改变核心功能、交互、美术方向或范围时再讨论。按下方路由加载相关技能并实施。
5. 最小目标完成后先交用户体验，等待反馈再进入下一阶段。简短说明已实现什么、能做什么，以及测试操作和预期效果；必要时说明未验证部分或阻塞。不要用复杂清单复述开发过程。

## 项目架构

设计或整理 RM 工程的地图、数据库组织与初始化流程时，读取[项目架构](references/project-architecture.md)。仅采用已确定的约定，尚未讨论的部分结合用户需求继续设计。

素材归档、工程目录组织与资源导入时，读取[项目目录架构](references/project-directories.md)，核对目标引擎及插件的实际加载路径。

## 项目管理

涉及分支、提交、版本收尾或工程整理时，读取[项目管理](references/project-management.md)。开发完成后引导用户验收；未经用户授权不得提交、合并或推送。每次修改前检查分支、工作区、暂存区和冲突状态。技能维护通用规范；用户提出文档相关需求时，执行项目管理中的文档维护流程。项目实际采用的通用规范、用户决定与自定义原则集中写入 `docs/`，`AGENTS.md` 只保留精简约束和入口，`docs/README.md` 按[总目录模板](references/docs-index-template.md)呈现基本信息和文档索引；实现变化同步修正相关文档，未确认建议不写成约定。

## 命名规则

新建或重命名事件、标签、插件、参数、本地化键及配音目录前，读取[命名规则](references/naming-rules.md)。所有命名约定在此集中维护；执行修改仍使用对应工程技能。

## 事件制作

决定公共事件封装，或涉及一次性流程、拾取、门与上锁的门、物品使用效果、临时图片或事件图像动画时，读取[事件制作指南](references/event-production.md)的相关章节。场景制作约定集中在本技能维护，执行时使用事件与数据库技能的正式接口。

## 制作手记

处理方案、视觉呈现或问题排查时，先按主题查看[制作手记索引](production-notes/index.md)，再读取相关条目。这里记录用户制作经验，与备选插件库分开维护；结合当前工程判断适用性，不将经验记录当作运行验证或自动修改授权。

## 素材

先检查用户素材，再明确告诉用户如何处理成可直接入工程的文件：按需求说明格式、尺寸、布局、帧数、命名和目录。素材制作、裁切等处理由用户完成；agent 写入并整合处理好的素材。没有素材时优先使用工程现有素材占位，并说明替换方式。

不建议自行制作素材。只有开发者明确允许 AIGC，且素材用途和规格已明确后，才可进入生成流程。完整游戏目标不自动授权生成素材。

## 选择实现方式

- 先检查工程已有插件是否能完整满足需求，避免重复实现或重复引入。
- 默认自行开发插件，一个需求尽量由一个 JS 完成。复杂需求直接设计插件开发。
- 仅当需求足够简单、基础界面方向模糊（菜单、标题、存档等），且候选插件恰好完整满足需求时，提出使用现成插件的方案。新增插件应功能专一、范围合适，不为小功能引入大型框架，不迁就插件改变需求。
- 通用、简单视觉效果优先检查备选库。最多涉及 1–2 个方法变动的极小需求，也可在事件页使用脚本命令；仍遵守事件修改流程。
- 阅读[备选插件库](references/plugin-library.md)进行选型。未经用户要求不搜索外部插件；库中存在不等于允许自动安装、启用或整套引入。
- 用户明确指定的复用偏好优先：滤镜用 FilterControllerMZ，不自行重写；常规立绘优先 LL_StandingPicture；配音评估 MUSH_Audio_Engine；跨存档数据评估 CGMZ_GlobalData 及其 Core 依赖。RPG Maker 官方附带插件整体属于候选范围，按具体需求核对，不自动安装全库。
- 涉及事件的解谜效果优先评估 VisuMZ Events and Movement Core；使用前必须阅读插件说明，并按[事件库架构](references/project-architecture.md#事件库)设置事件库与加载配置。
- 编写插件前读取[插件开发规范](references/plugin-development.md)。

参数配置先通过 rpgmaker-plugins 的 `manual` 读用法，再通过 `help` 查询相关参数结构及当前值；默认不直接阅读源码注释，必要兜底条件以插件技能为准。

## 协调工程技能

本技能负责决策，不另造文件写入脚本。执行时依赖相邻技能目录；分发制作工具集时一起提供。缺失时说明具体缺失能力，不用临时写入器绕过。

| 工作 | 必须读取与使用 |
| --- | --- |
| 插件查询、参数/命令帮助、源码开发和注册 | [rpgmaker-plugins](../rpgmaker-plugins/SKILL.md)：`scripts/plugins.py`；源码可正常编辑，任何 `plugins.js` 修改及恢复只能通过正式脚本 |
| 任意数据库字段修改 | [rpgmaker-database](../rpgmaker-database/SKILL.md)：正式数据库 API/`scripts/database.py`，不直接改目标 JSON |
| 地图事件、公共事件与指令 | [rpgmaker-events](../rpgmaker-events/SKILL.md)：`scripts/event_api.py`，按支持状态选接口，由正式后端写入 |
| 运行游戏验证 | [rpgmaker-playtest](../rpgmaker-playtest/SKILL.md)：按其会话流程操作，结束或失败后关闭本次进程 |

以上链接相对于本文件应指向同级技能；安装时保持相邻目录。脚本能力不足时先扩展正式脚本并验证，不绕过预览、指纹或恢复流程。

## Steam 接入

涉及 Steam 安装与整合时读取[安装手记](production-notes/how-to-integrate-steam.md)，先核对发布运行时和原生库配套，再使用[关键脚本接口](references/plugins/cyclone-steam.md)。不要把终端 Node.js 版本代替 NW.js 环境，也不要将初始化成功当作云存档或成就已验证。

## 测试边界

开发默认开新存档测试，运行状态默认随正常存档保存。先检查已有专用测试场景；没有用户明确要求，不新建测试地图或测试事件，提供可执行的测试流程。已有测试场景也不意味着可以自行创建测试事件。

验证完整核心流程，涉及持久化时验证保存、读档；区分静态检查、脚本测试和实际游戏测试。未运行的测试明确说明。避免大量预防性兼容代码；已发布并推送的功能，按用户需求设计兼容层。
