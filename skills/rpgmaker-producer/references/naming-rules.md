# 命名规则

统一维护游戏制作中的命名约定，其他技能与制作手记引用本文，不重复维护规则。新建或明确要求重命名时使用；不因规范整理而批量重命名既有工程。显示名称使用用户偏好语言，内部标识保持稳定；具体工程已确认的约定优先。接口要求、文件格式和插件固有语法仍见对应技能。

## 地图命名

地图可按具体地点命名，例如「旧街」「餐厅」「教室」；里世界等以角色经历为核心的区域，也可按角色命名，例如 `Ethan的记忆`，便于在地图树中辨认归属。角色与地点名称使用项目中的实际内容，不固定套用示例。

被明确标记为废弃的地图，重命名为 `原地图名（废弃）`，例如 `旧街（废弃）`、`Ethan的记忆（废弃）`。保留原名并使用全角括号，不重复添加后缀；未使用或未查到引用不等于已被标记废弃，不自行判定。

## 事件命名

地图事件使用简短、能说明用途的名称，例如“门卫”“宝箱”“入口传送”，不要求添加 ID 和类别前缀。

公共事件按游戏语言命名：中文使用 `【类别】事件名`，英文使用 `<Category>Event Name`，类别括号为半角 `<` 和 `>`。

- 名称中不包含公共事件 ID 或编号前缀；实际数据库 ID 保持不变。
- agent 优先使用本文已约定、用户明确指定或工程已有且适用的命名规则与类别。不得自行新增、推导或扩展类别；没有合适类别时先与用户确认。工程已有类别不代表可以照样新增其他类别。
- 事件名简短说明用途。
- 用户明确允许使用「功能」类别：中文 `【功能】事件名`，英文 `<Function>Event Name`，例如 `【功能】启用灯光`。

示例：

```text
【功能】启用灯光
【系统】初始化游戏
【剧情】第一章序幕
```

英文游戏示例：

```text
<Function>Enable Lighting
<System>Initialize Game
<Story>Chapter 1 Prologue
```

新建或按用户要求重命名公共事件时遵守此格式。仅修改既有事件指令时，不擅自批量重命名其他事件。公共事件名称通过数据库正式脚本修改，不能直接编辑 JSON。

### 公共事件名称的取法

- 物品使用效果：使用对应物品名，例如 `【物品】旧钥匙`。
- 主线、支线长剧情：需要封装时使用剧情内容名称，沿用 `【剧情】`，不新增「演出」类别；短对话与短效果不因此封装为公共事件。
- 音效：使用音效名或使用场景，例如 `【音效】玻璃破碎`、`【音效】获得物品`。
- BGM：使用代表性场景名，例如“标题”“安全屋”；不要求每首 BGM 都建立公共事件。
- 系统功能：名称说明对话框位置、大小或功能启停等用途。

以上示例不扩展可用类别。BGM、并行循环、收集物等使用工程已有且适用的类别；没有合适类别时先向用户确认，不直接把用途词转成新类别。封装范围见[事件制作指南](event-production.md#公共事件封装原则)。

## 公共事件列表分隔

分隔名称使用短标题，两侧各固定 9 个半角短横线 `-`，标题与两侧横线之间各留一个半角空格，例如：

```text
--------- 开场 ---------
```

横线数量固定，不随标题长度调整。分隔行属于功能区标题，可不使用普通公共事件的类别命名格式。

- 仅在划分游戏不同大功能区时少量使用，不为每个事件或小分组添加分隔。
- 功能区间按[项目架构](project-architecture.md)分配，在大区段边界设置分隔；不因添加分隔而自动移动或重编号事件。
- 使用专门的空公共事件作为分隔，指令列表留空（保留引擎结束标记），触发方式设为无；不要覆盖已有功能事件或被引用的事件。

### 特定用途事件

命名为 `门（目的）` 或 `Door（目的）`，例如 `门（商店）`、`Door（Shop）`。

物品效果登记调用该公共事件，公共事件按物品命名，沿用类别规范，例如 `【物品】旧钥匙` 或 `<Item>Old Key`。

## 标签命名

标签使用简短、可读的自然语言，可用中文，例如 `使用失败`、`使用成功`。英文首字母大写，单词之间用空格，不使用下划线或连字符，例如 `Use failed`、`Use successful`。Label 与 JumpToLabel 必须使用完全相同的名称，同一指令列表中标签名应唯一。修改已有标签时同步更新对应跳转。

## 插件文件与标识

默认 `前缀_插件名.js`。可复用引擎系列用系列代号（Grace、Liy）；作者系列用作者名（如 Kui）；游戏专用插件用游戏简称或较短全名（Ve、Veloria）。沿用工程已有约定，不自动把用户当作葵。

只有用户要求开发整套插件时，考虑 `前缀_序号_插件名.js`：0 为基础功能和依赖，1 为进阶功能（常依赖 0，也可能独立但功能有限），2 及以上为特殊场景；不是开发流水号，序号不宜高，多数属于 0。

一个需求尽量一个 JS。为游戏复用的基础、高频代码放入 `游戏_Core.js`，例如 `Ve_Core.js`；不为单次功能强行拆分或建设通用框架。

- `@author` 写用户指定的作者名；未提供则写实际 agent 名称，例如 Codex，不写字面量 user。
- 参数 ID 用 `功能:参数名`，如 `message:size`。功能名很长时可用不歧义的首字母缩写，保持一致。冒号表达功能划分，类型通过 `@type` 声明，不照搬 Visu 的类型后缀编码约定。
- 命令参数直接命名，如 `actorId`、`outfitId`。

## 本地化键命名规范

用户约定的分类前缀：

| 内容 | 前缀 |
| --- | --- |
| 物品 | `item` |
| 人物 | `actor` |
| 对话 | `dialogue` |
| 系统 | `system` |

名称使用 `xxx.[index/id].name`，描述使用 `xxx.[index/id].desc`。`xxx` 替换为分类前缀，`[index/id]` 替换为实际编号或标识，不保留方括号。例如：`item.001.name`、`item.001.desc`、`actor.veloria.name`、`actor.veloria.desc`。

编号或标识沿用用户确定的对应关系；保留已有前导零，`001` 只是示例，不强制所有编号为三位。系统提示等不属于名称或描述的文本，其余层级和后缀按需求讨论，不自动套用 `.name` 或 `.desc`。

### 特殊系统的命名空间

`item`、`actor`、`dialogue`、`system` 不是封闭列表。收集系统、战斗系统等有独立文本体系时，可以另起命名空间，例如 `book.`、`battle.`、`paper.`，不必全部归入 `system` 或 `dialogue`。

命名空间按功能或内容类别确定，并在同一工程内保持含义一致。名称、描述仍沿用 `.name`、`.desc`，例如 `book.001.name`、`book.001.desc`、`paper.001.name`；其他文本的后续层级按该系统需求确定，不强制套用名称、描述或对白的结构。上述命名空间是用户提供的示例，不预设其具体功能或自动创建配置。

### 对白键

统一使用 `dialogue.类别或对象_编号.对话号`，不分章节。类别或对象可用 `main`（主线）、`side`（支线）、`chat`（通用闲聊），也可直接用 `flower` 等交互对象名称；不限定为三种对白类型。剧情类别后的编号表示剧情段落，对象名称后的编号表示对象。例如：

```text
dialogue.main_01.001
dialogue.main_01.002
dialogue.side_01.001
dialogue.chat_01.001
dialogue.flower_01.001
```

`dialogue.main_01.002` 表示主线第一段剧情的第二句话。`dialogue.flower_01.001` 表示花 1 的第一句交互对白，不额外插入 `chat` 层。对话号固定三位数字，不足补前导零，从 `001` 开始；段落或对象编号示例为 `01`。此规范替代此前暂定的 `dialogue.对象ID.台词编号`，不再加入章节层或章节罗马数字。

不同时间、任务阶段说哪句，由事件条件决定。制作表另列「对象名称」「触发条件」帮助辨认，例如“守卫／初次交谈”“守卫／任务完成后”；这些是维护信息，不当作语言列，交付插件读取的 TSV 时按原版要求整理。键在表内唯一，不靠添加场景、地点或不断延长短标签解决重名。不据此自动重命名已有工程的键。

## 配音目录与编号

可在 `audio/vsc/` 下创建子目录，保持目录清晰。根据工程需要选用以下分类方式，不默认强制叠加两层：

- 按章节：`chap01`、`chap02`，小写 `chap` 加两位数字。
- 按角色：角色名小写，例如 `veloria`。

音频编号与台词对应关系、具体编号规则先与用户确认，不自行按事件顺序或文件顺序推断。`001` 仅为示例，不将对白键的三位编号规则自动套用于音频文件。

## 开关与变量

变量 1–10 的名称固定为 `x1` 至 `x10`，作为通用临时值。11–20 为坐标、条件等专用临时值，具体名称与编号对应尚待确定；分区见[项目架构](project-architecture.md#变量)。

其余开关与变量当前采用简短中文名称，直接说明含义，不加编号前缀。需要区分同类内容时补充对象名称，不自行添加类别。

| 类型 | 命名示例 |
| --- | --- |
| 坐标变量 | `临时X`、`临时Y`、`目标X`、`目标Y` |
| 条件变量 | `临时条件` |
| 数值变量 | `对话次数`、`剩余时间`、`收集数量` |
| 完成状态开关 | `旧钥匙已取得`、`钟楼解谜已完成` |
| 功能开关 | `允许菜单`、`显示交互提示` |
| 运行状态开关 | `追逐进行中` |

开关名称须明确 ON 时的含义；变量名称须说明存储内容。这些类型用于解释示例，不作为名称中的类别前缀。示例不固定具体 ID；先查询工程已有编号、用途和引用，再按分区分配。用户暂定采用此命名方案，后续可按实际维护情况调整。

## 素材文件与目录

来源：[Veloria 2 文档命名规则](https://github.com/Moiyri/veloria-2-docs/blob/main/xiang-mu-jia-gou/ming-ming-gui-ze.md)，读取版本 `8df79e5`。已修正 RM 前缀说明、配音拼写，并结合当前对白键与配音目录约定整理。

文件／自建目录使用英文与半角符号，单词以 `_` 连接；文件名单词首字母大写，缩写全部大写；自建目录小写，通常采用复数。引擎固定目录、插件规定标记、语言代码和已确认的配音目录约定优先，不据此重命名 `data`、`js`、`audio/vsc/chap01` 等目录。此规则用于资源文件路径，编辑器中的地图、事件、开关和变量显示名称仍按本文各自规则。

### 图像

| 类型 | 格式或示例 |
| --- | --- |
| 角色行走图 | `[RM前缀]角色名_状态_版本`，如 `$Veloria_Walk.png`；角色用英文名，不含姓 |
| 无名 NPC | `NPC_身份两位编号`，如 `$NPC_Villager01.png` |
| 物体行走图 | `Obj_物体两位编号`，如 `!$Obj_Table01.png` |
| 多帧行走图 | 加 `%(帧数)`，如 `$Veloria_Walk%(4).png` |
| 立绘 | `Standing_角色名_表情`；表情如 Normal、Happy、Smile、Sad、Angry、Surprised、Thinking |
| CG | `CG_章节_名称_后缀`；章节可省略，存在时用 ChapX，后缀用于连续画面或版本 |
| 地图图层 | `Map三位ID_层级及序号_混合模式`，如 `Map002_L0_Normal.png` |
| 图块 | `Tile_主题_编号或变体_来源`；旧项目未强制执行，不据此自动改名 |
| UI | `UI_元素_状态`，如 `UI_Button_Normal.png`、`UI_Window_Menu.png` |

一个主要角色或状态通常单独一张行走图，NPC 可按需要合并。`$` 表示单角色图，而非默认的八角色图；只对符合单角色布局的素材使用。`!` 表示物体角色图，取消引擎默认向上偏移，常用于门、宝箱等，不是普通角色必加标记。

多帧标记由 [GALV_CharacterFramesMZ](plugins/galv-character-frames.md) 提供，必须核对插件是否启用及 Filename Symbol 是否仍为 `%`，同时检查素材实际帧数。

地图图层：BG 为背景（z=-1），L 为人物下方（-1<z<3），U 为人物上方（z>3）；可选序号从 0 开始。混合模式用 Normal、Additive、Multiply、Screen。名称只是提示，实际层级与渲染顺序由图层配置决定。

### 音频

| 类型 | 格式 |
| --- | --- |
| 配音 | `Voice_故事段落或说话对象_文本ID_语言` |
| BGM | `BGM_对象或场景或主题或曲名_描述_变体` |
| 环境音 | `Amb_地点_状态` 或 `BGS_地点_状态` |
| 音效 | `SE_对象或类型_动作_变体` |

配音统一拼写为 `Voice`，不使用旧文档的 `Vocie`。沿用当前不分章节的对白键组织，例如 `dialogue.main_01.001` 可对应 `Voice_Main_01_001_zh_CN.ogg`，`dialogue.flower_01.001` 可对应 `Voice_Flower_01_001_zh_CN.ogg`；具体对应表仍须与用户确认。这是完整文件名示例，不要求将已确认使用纯编号的音频批量改名，子目录继续按本文配音目录规则。

BGM 和 SE 的变体通常用两位数字，例如 `BGM_Garden_Night_01.ogg`、`SE_Door_Open_01.ogg`。音频来源、作者与授权通过表格记录，不塞进文件名。涉及插件按文件名生成变体（如脚步声）时，按插件要求确定数字后缀，不能直接套用普通 SE 示例。

格式沿用旧文档约定：图片 `.png`、音频 `.ogg`、视频 `.mp4`／`.webm`、脚本 `.js`、字体 `.ttf`；具体导入仍核对目标引擎与插件支持。

## Git 分支与提交信息

长期分支名为 `main`（正式版）、`develop`（开发）。工作分支使用简短英文：`feat/目标`（新功能）、`fix/问题`（开发问题修复）、`hotfix/问题`（正式版临时修复）、`chore/事项`（整理维护）。例如 `feat/diary`、`fix/hiding-door`、`hotfix/save-crash`。创建基线与发布条件见[项目管理](project-management.md#分支管理)。已有适用工作分支时沿用，不因任务自动另开重复分支。

普通提交标题格式为 `类型(范围): 中文说明`，类型与括号之间不加空格。范围可省略；标题具体、简短，不仅写“更新”“修改”或“优化一下”。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能、剧情或玩法内容 |
| `fix` | 修复问题 |
| `asset` | 素材新增或替换 |
| `refactor` | 保持行为的结构调整 |
| `docs` | 文档与制作约定 |
| `chore` | Git、工具与工程维护 |

已确认范围为 `event`（事件）、`locale`（本地化）。其他范围先确认，不从用途自行推导新范围。跨多个模块且没有明确主模块时可省略范围。

```text
fix(event): 修复躲藏结束后门无法打开
fix(locale): 修复物品名称的本地化键
feat: 完成日记阅读与躲藏流程
```

复杂提交正文说明修改原因、主要变化与验证结果，简单提交不强制写正文。

正式版本收尾提交使用特例格式 `update: update to <版本号>`，例如 `update: update to 1.2.0`。`update` 仅用于正式版本收尾，不替代普通提交类型。正式版本 tag 指向版本收尾的 update 提交，使用版本名；`v1.xx`、`1.x.x` 等形式均可，按用户偏好并沿用项目已确认格式，不强制 `v` 前缀。未能从项目或对话确定具体版本名时先确认。提交时机与操作流程见[项目管理](project-management.md)。
