# 插件开发规范

## 命名与组织

插件文件、基础库、作者署名、参数与命令参数的命名统一见[命名规则](naming-rules.md)。一个需求尽量一个 JS；基础、高频代码放入游戏基础库，不为单次功能强行拆分或建设通用框架。

## 编辑器声明

- `@plugindesc [v1.0.0] [换装系统] 描述`：版本、功能类别、简短用途。
- 显示名称、说明、帮助、选项使用用户偏好语言；未指定则沿用对话语言。内部标识符保持稳定。
- 长参数列表可用 `BreakHead`、`BreakSettings1` 等装饰参数分隔，并配合 `@parent` 分组；简单列表无需分隔。装饰项不作为运行数据。
- 根据用户实际需求提供可直接在事件编辑器选用的插件命令，不预设庞大命令集。命令参数命名见上述规则。
- 动态执行或固定功能难覆盖的需求可以提供 JS 扩展点；明确执行时机、上下文变量、`this`、返回值及最小例子，不把所有参数都做成 eval。

## Help 写法

沿用 VisuMZ 的编辑器内手册风格，使用原创说明与示例，不复制整篇第三方手册。大分隔线划分功能章节，小分隔线划分条目；按读者实际操作顺序写。内容短则保持短，仅包含适用章节：

1. 功能介绍、适用引擎、前置条件与加载顺序。
2. 快速开始：编辑器操作路径、最少配置、素材准备、可看到的结果。
3. 复杂功能按步骤说明，给具体例子。
4. 插件命令说明效果、适用场景、相似命令差异；参数写清单位、特殊值及限制。
5. 参数按功能分组，解释相互影响和默认行为，不重复整段教程。
6. 若有备注标签，写明填写位置、适用对象、语法、替换值和回退行为。脚本接口和 JS 扩展点提供执行上下文与例子。
7. 必要的注意事项及版本变更。

帮助应能独立指导用户使用；聊天交付简短不意味着删掉必要帮助。不要保留空章节。

## 配置与存档

大部分需求使用 RM 参数管理器，按需使用结构体和数组。保留 YAML/JSON 外置配置能力，只有复杂功能、大量文件或复杂列表才考虑使用；配置位于工程根目录 `data/` 下的专用目录或直接位于根目录，并提供相应解析器与读取流程。不默认维护双套配置。

需要持久化的游戏运行状态默认写入正常存档并随读档恢复，临时缓存、动画过程不必持久化。开发通常新存档测试；不要花时间编写大量兼容代码。已发布并推送且用户有需要时，再处理旧存档兼容。
