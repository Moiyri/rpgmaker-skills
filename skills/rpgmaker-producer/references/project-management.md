# 项目管理

目录组织见[项目目录架构](project-directories.md)；分支名、提交类型和信息格式统一见[命名规则](naming-rules.md#git-分支与提交信息)。项目文档与 AGENTS.md 的维护见本文后续章节。

## 每次修改前的状态检查

每次修改开始前，先确认当前分支、工作区已修改／未跟踪文件、暂存区内容，以及是否存在未完成的合并、变基或冲突。核对本次目标与已有改动的归属，记录修改前状态作为本次任务基线。不得覆盖用户已有改动，也不自动 stash、清空暂存区或重置文件。

已有冲突或中断的 Git 操作先单独处理。需要切换分支而工作区不干净时，先判断能否保留现有改动；存在归属不明或覆盖风险时向用户说明，不强行切换。

## 分支管理

长期维护 **main、develop** 两个分支。develop 从 main 分出，作为日常开发与集成分支。

| 分支 | 创建基线 | 职责 |
| --- | --- | --- |
| `main` | 正式版本主线 | 始终保存准备发布的正式版 |
| `develop` | `main` | 日常开发与集成 |
| `feat/目标` | `develop` | 新功能开发 |
| `fix/问题` | `develop` | 修复开发中的问题 |
| `hotfix/问题` | `main` | 正式版的临时问题修复 |

一个工作分支对应一个完整目标，已有适用分支时沿用。创建前确认本地基线和已有分支用途，分支重名不自动删除或覆盖；需要同步远程时先核对工作区，不盲目 pull。维护类工作分支可沿用 `chore/事项` 命名，基线使用 develop。

main 必须保持正式版，不能随意直接提交或合并。正常发布必须完成版本更新、测试功能清理、正式参数还原和发布验证，准备发布后才允许将开发成果合入 main。

hotfix 从 main 创建，仅处理正式版临时问题；修复、验收并更新小版本号，完成正式配置检查后，在用户授权下合并回 main。具体版本递增方式按项目约定与用户确认，不擅自把“小版本”解释为固定某一位。feat 的合并和 hotfix 回流规则见下文；bug 修复与正式发布的合并方式分别规定。

提交、合并、推送各按用户授权执行；分支规范不构成自动操作授权，不擅自重写历史。

## 提交时机与粒度

**一次完整改动对应一个提交**，按目标划分而非按文件数量划分：一次 bug 修复可以涉及多个事件；一个新流程的实装可以同时包含多个地图、资源、事件、开关和插件调整。相关依赖一起提交，使每个提交保持完整。

开发完成后，简短告知用户已实现的功能、验收方法与预期效果，并引导其验收后提交，例如：“已完成躲藏流程，请测试阅读日记、触发躲藏和出门；验收通过后可提交这次改动。”**不得私自提交；验收通过本身不等于提交授权。** 用户已经明确授权的提交按授权范围执行，不重复索要许可。未授权合并或推送时不自动执行。

项目管理或历史工作区混乱时，尽量区分功能、修复、素材、文档及工程维护等改动。先查看并整理改动范围，无法可靠划分的部分说明给用户，不将所有杂乱内容笼统提交成一次修复，也不撤销用户已有改动。

## 正确提交流程

1. 检查当前分支、工作区、已有暂存内容与 diff，确认本次完整目标和用户已有修改。
2. 按实际工程编写／检查 `.gitignore` 与 `.gitattributes`。素材建议使用 Git LFS，确认新增文件实际受规则跟踪。
3. 完成适用验证，向用户说明验收方式及实际验证范围；获得提交授权后继续。
4. 按文件或修改块暂存本次范围，不以 `git add .` 代替范围检查。保护用户原有暂存内容，不把它默认为本次范围。
5. 检查暂存区 diff，确认依赖齐全，没有混入无关改动、存档、临时文件、备份或凭据。
6. 按规定格式提交，再核对提交内容和工作区状态。失败先处理原因，不跳过检查。

## RM 共享配置文件

特别检查 **`data/System.json`、`js/plugins.js`、`data/MapInfos.json`**。这里使用引擎实际文件名，分别对应用户提到的 System、plugin 和 MapInfo 文件。

这些文件容易被编辑器操作顺带修改；地图编辑器的观察位置等也可能造成地图数据差异。同一文件可能混有多个开发目标的修改，不能因本次涉及其中一项就整份纳入提交。

只提交当前修改范围内的文件和变更：涉及共享文件时逐项核对实际 diff，考虑必要性和关联关系后选择提交内容；无法安全分开时向用户说明。不能为了整理提交而直接改写目标 JSON 或 plugins.js，工程写入仍使用对应正式技能脚本。

发生合并冲突时单独核对双方的功能、地图 ID、加载顺序、参数和引用关系，再按正式接口解决；不整份选择某一侧覆盖。解决后重新检查完整功能。

## 忽略与 Git LFS

`.gitignore` 按实际目录排除存档、日志、缓存、临时文件、备份和构建输出；测试地图、测试事件属于工程内容，不一律忽略。当前技能仓库仍遵守用户已有的 test／tests 不提交约定，不把它扩展成所有游戏项目的通用规则。

图片、音频、视频、字体和特效等二进制素材建议使用 Git LFS；跟踪规则写入并提交 `.gitattributes`。JSON、JS 和文档通常使用普通 Git。已有素材迁移若涉及历史重写，须单独确认；不因建议 LFS 就自动改写历史。

## 功能分支的合并

**一条 feat 对应一次 squash**：一个功能分支中的多次操作与提交，在功能完成、用户验收并授权合并后，汇总为一个完整功能提交合入 develop。提交使用 `feat` 类型，描述最终实现的功能，不罗列中间开发操作；不混入无关目标。

## Hotfix 回流 develop

hotfix 合回 main 后，将修复同步到 develop 前，必须先获得用户对此次回流合并的许可，并检查 main 与 develop 的提交历史关系。

- 历史相似、改动关系清楚时，可在授权范围内将包含 hotfix 的 main 合入 develop；仍核对版本收尾文件与开发参数，处理冲突并验证。
- 历史不相似或明显分叉时，先确认 develop 的历史是否已包含在 main，以及是否有尚未进入 main 的改动。检查双方独有提交、祖先关系及实际 diff；squash 可能导致提交不相同但改动已存在，不能只凭提交数量或哈希判断。
- 将检查结果简短告知用户：develop 是否有未发布内容、修复与版本参数的差异，以及建议的处理方式。存在不确定或未验收内容时明确说明，不直接合并或删除分支。

用户通常采用的处理方案是：**将 develop 的修改一并合入 main，作为一个新的小版本发布，随后删除旧 develop，再从更新后的 main 创建 develop**。这是需要用户确认的重整与发布方案，不是遇到历史分叉就自动执行。

采用该方案前核对 develop 内容是否均可纳入本次发布并完成验收；按正式发布流程恢复参数、更新版本、提交 update 并打 tag。旧 develop 的所有拟保留改动已纳入、工作区与未推送内容已检查，且获得分支删除授权后，才删除并重建。本地与远程分支清理分别按授权处理，不自动强制删除或强推。

## Bug 修复的合并

一次 bug 修复可能包含多次操作、调试和相关提交。合入目标分支时使用 **squash**，将该问题的完整修复汇总为一个提交：fix 的目标是 develop，hotfix 的目标是 main。只汇总属于该问题的改动，不包含其他任务。

提交标题说明“修复了什么问题”，例如 `fix(event): 修复躲藏结束后门无法打开`，无需逐项罗列中间操作或每次调试。必要正文保留原因与验证结果，标题仍遵循命名规则。hotfix 还需完成小版本更新与正式配置检查。验收和相应提交／合并授权仍然适用。

## 正式版本收尾与合并

develop 可能包含多个 feat、fix，正式发布时使用 **普通 merge** 合回 main，不将整个版本 squash 成一个功能提交，以保留各项改动历史。

发布前确认版本内容已完成并验收，检查正式参数、测试功能与恢复清单，准备发布后才开始合并。用户授权的正式发布流程按以下顺序执行：

1. 将 develop 普通 merge 到 main；冲突单独处理并验证，不能整份覆盖共享配置文件。
2. 在 main 上完成必要的版本收尾：通过数据库正式接口更新 title，更新该版本需要的 System 等文件，恢复正式版参数并关闭测试时临时开启的功能和开关。保留正式功能所需状态，不一律将所有开关设为 OFF。
3. 核对正式启动、关键流程与最终 diff。提交该版本收尾所需文件及变更，提交信息为 `update: update to <版本号>`。版本完整内容已由前一步 merge 带入，不因收尾而混入未验收的无关改动；仍遵守 ignore、LFS 和正式写入接口。
4. 在 update 提交上打正式版本 tag；tag 命名见[命名规则](naming-rules.md#git-分支与提交信息)。正式发布以完成收尾、验证和 tag 的版本为准，不把中间 merge 状态当作已发布版本。

版本收尾涉及的公共系统文件修改可以直接在 main 上提交为 update；仍逐项检查修改范围，仅纳入当前版本的正式参数与版本设置。main 上的 update 是明确的正式发布收尾操作，不允许借此随意直接开发或提交。提交、合并、打 tag 与推送按用户授予的操作范围执行，已有完整发布授权时不重复询问；未授权时引导用户确认，不自动执行。分支、tag 的远程推送规则与普通发布收尾修改回流 develop 的方式后续确定；hotfix 回流按前述专门规则处理。

## 项目文档与 AGENTS.md

### 执行时机

用户提出文档相关需求（如整理、创建、更新项目文档或 AGENTS.md）时，执行本节流程：检查已有文档，按项目实际情况整理结构，记录已确认约定，并更新目录和相关引用。仅问文档内容或位置时按问题回答，不将普通查询扩大为文档重构。普通开发不因存在这套流程就自动搭建完整文档体系；已有文档涉及的实现发生变化时，仍同步修正相关内容。

### 统一规范与项目约定

技能维护所有项目通用的制作规范。项目文档同时供用户和 agent 阅读，保存当前工程实际采用的规则、用户确认的决定和项目自定义规范。**具体细节集中在 docs，AGENTS.md 保持精简。**

命名原则、插件使用偏好等即使已存在于技能，也需要在项目文档中说明当前项目实际采用的内容，并引用对应通用规范。不只让用户去技能中寻找规则，也不复制全部与项目无关的技能内容。项目专用原则、例外和定制流程写入对应文档，说明适用范围；未经确认的建议不能写成正式约定。

### 初版 docs 目录

```text
docs/
├── README.md          基本信息与文档目录
├── workflows/         测试、打包、发布与运行环境
├── architecture/      地图、数据库、目录及编号分区
├── visuals/           色调、效果、插件用法与示例
├── design/            人物设定、剧情大纲与游戏策划
├── ui/                界面设计、交互与素材要求
├── systems/           游戏系统设计与实现
└── development/       命名、编程、事件与项目定制规范
```

按主题组织目录，每个实际使用的目录以 README.md 提供说明与索引，具体文档按需求增加。docs/README.md 按[总目录模板](docs-index-template.md)呈现基本信息与文档链接；新增、移动或删除文档时同步相关链接。具体设计、流程和经常变化的内容维护在对应主题文档。

- workflows：明确运行和测试入口、角色初始位置、正式发布参数恢复清单、打包发布流程、NW.js 及其内置 Node.js 版本等。
- architecture：地图组织与连接、角色／物品／开关／变量／公共事件等编号原则，已有编号段的意义；未约定的区间不自行编造。
- visuals：画面色调、效果数值和时机、实际使用插件、配置与示例。
- design、ui、systems：分别维护策划内容、界面和游戏系统的设计与实际状态。
- development：项目采用的命名和制作规范，以及定制化调用。例如对白是否使用本地化、配音、立绘，具体插件、参数、指令和调用顺序；不能默认所有项目直接使用原版显示对话流程。

插件选型与使用偏好记录到相关功能目录，公共开发约定放 development；同一项规则在一个地方维护，其他地方链接引用。

### 精简 AGENTS.md

AGENTS.md 保留必要项目识别、适用技能、少量必须执行的约束与 docs/README.md 入口。不展开地图 ID、插件参数、素材对应表或正式参数恢复清单等细节，以链接指向 docs 的对应文档。不在其中增加“修改前必读”这类默认行为提醒。

用户确认的长期决定写入相应 docs 文档；需要新增入口或简短执行约束时同步更新 AGENTS.md。修订已有决定时更新原条目，清理矛盾与过时内容。无法判断是否取代旧规则时先确认，不仅把决定留在聊天中。

### 维护原则

先查已有文档，在原位置维护同一主题，不为每次任务重复建同类文档。文档描述当前实际状态，区分已确认方案、已实现功能和未验证部分；保留历史方案时标明状态。实施改变已记录的行为、路径或操作方式时，更新对应说明及目录链接。

任务流水、临时日志和猜测不当作长期规范。文档更新与相关功能改动纳入同一完整提交范围，仍遵守验收和授权规则；不能通过更新 AGENTS.md 自行新增提交、合并或推送的授权。
